# 自动执行只服务 issue：PR 候选只走我来开

dsh-l v2 的内置工作流只有一条交付语义：克隆默认分支、另起工作分支、实现、验证、G2 放行后推送并发起新 PR——它默认候选是 issue，却对 PR 候选同样可点。2026-11-23 PR80 实录（run-1795335897221-1e28）暴露了后果：引擎没有检出 PR 的 head 分支，在 main 上照任务包重做一遍改动，G2 放行后另开了同主题的 PR81。据此 /grill-with-docs 拍板（Q27–Q28）：自动执行只为 issue 候选创建，把 issue 变成 PR 是引擎唯一的工作；PR 候选只有「我来开」一条路，由主人在会话里与 GitHub 上处理（分支名与 `gh pr checkout` 写进开工消息，不自动切换本地检出）。引擎为 issue 新开的 PR 记在来源候选上作为交付，摄取时不再把它收成候选。G2 对所有候选只有一个含义：交付前。

## Considered Options

- 维持单一流水线，只在确认弹窗里警告「将基于 main 新开分支并另开 PR」：实现最小，但 PR 候选的执行结果仍是重复 PR，警告只是把错误交给主人。
- 为 PR 另做一条模板（评审并修复后推回原分支）：要新增模板、角色、推回逻辑与无推送权限降级，而这条路径从未被真实需要过；本机 PR 候选以 dependabot、Devin 这类自动化 PR 为主，终点是合并或关闭。
- 为 PR 做只跑验证脚本的短模板：成本较低，但 GitHub Actions 已承担验证；留作日后有真实需要时的增量，不预先建设。
- 自动执行只服务 issue（选定）。

## Consequences

- 引擎内核不变（状态机、模板快照、三道人工闸门、确定性检查）。`/run/start` 与 `candidate/gate` 对 PR 候选拒绝（409），行内不出「自动执行」。
- 一次交付只有一个候选：引擎开的 PR 以「PR #n · 待合并 / 已合并」挂在来源候选上，「产出候选」概念作废，「上游关闭不代作主」不设例外。
- G2 不再按候选类型分化；GLOSSARY「开工」「交付」「闸门」已同步。
- 细则见 docs/design-v2.md §20 第 29、30 条。
